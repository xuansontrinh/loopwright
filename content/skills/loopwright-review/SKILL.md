# loopwright review

Reviewers judge in their own context. This thread dispatches them, merges their verdicts, asks the user about undecided findings, and records the result. Do not fix code here.

## Setup

1. Run every loopwright command from the worktree root: `cd "$(git rev-parse --show-toplevel)"`.
2. `node "{{LW_HOME}}/hooks/lw.mjs" brief reviewer` → `dir` (`<lw>`), `task` (relative to `<lw>`), `baseCommit`, `config` (`crossAgentReview`, `crossAgentReviewer` = `models.crossAgentReviewer`; missing → `off`; `simplify`), `effort`. `dir` `null` inside a git repo → no task has started here yet; `lw.mjs start` creates `.loopwright/` with the first task, so continue and `task: null` reports "no active task". Not a git repo → tell the user loopwright must run inside a git repo, stop.
3. `task: null` → "no active task": point the user to `/loopwright-flow`, stop.
4. Read the task file header (`tier`, `two-pass`, `fix-round cap`).
5. Scope: small/standard → the task. Large → the first `S<n> [tested]` slice, or `whole` once every slice is `[passed]`.
6. Round `n` = number of `- R` lines in `## Review log` for this scope after the last `- Scope change:` line (all of them if there is none) + 1.
7. Moved branch. `headMoved` in `brief` (new commits since the base commit, at least one already on the upstream branch, and not answered yet for this HEAD) → run `node "{{LW_HOME}}/hooks/lw.mjs" await-user "branch moved"`, list the commits to the user and ask one question: are they pulled commits (leave them out of the review) or this task's own commits (keep them in)? After the answer run `node "{{LW_HOME}}/hooks/lw.mjs" resume` and record it as a decision `D<n> [asked]`.
   - `headMoved.keptEarlier` → an earlier answer kept commits in the review, so the branch holds both kinds whatever the answer: list only the new commits, and a 'pulled' answer takes the keep-base path below, with the both-kinds notice.
   - `headMoved.localOnly` → the listed short shas exist only locally, so they are the task's own work and the branch holds both kinds whatever the answer: a 'pulled' answer takes the keep-base path below, with the both-kinds notice. Never judge this from the commit subjects.
   - Pulled → run `node "{{LW_HOME}}/hooks/lw.mjs" start <task> --force --base HEAD && node "{{LW_HOME}}/hooks/lw.mjs" stage build` as one call (Passes step 1 sets the stage to review), update `base commit` in the task file header to the new HEAD, run `node "{{LW_HOME}}/hooks/lw.mjs" accept-locks --restart --reason "<the decision in words>"`, then run `brief reviewer` again (the base commit changed).
   - This task's own commits, or a branch holding both kinds → run `node "{{LW_HOME}}/hooks/lw.mjs" keep-base --reason "<the decision in words>"`; the base stays. Both kinds: add `--pulled` to that command, so the locked tests the new commits changed show in `pulledLocks` (run `brief reviewer` again, then step 8), and tell the user the pulled commits stay in the review, because the base cannot move past the task's own commits.
8. `pulledLocks` in `brief` (a pulled commit changed those locked tests) → before the first reviewer is spawned, send only the listed files to Test: `node "{{LW_HOME}}/hooks/lw.mjs" reopen test "<the pull decision in words>"` when Build has begun, `node "{{LW_HOME}}/hooks/lw.mjs" stage test` otherwise, then run `/loopwright-test` for those files. After the tester re-locked them, run `node "{{LW_HOME}}/hooks/lw.mjs" accept-locks --reason "<the pull decision in words>" <path>…` with the `pulledLocks` paths, so the re-locks are accepted under the pull decision, and continue with step 9 and Simplify.
9. `flaggedLocks` in `brief` (present only while a re-lock or forced restart is flagged and not accepted) → before the first reviewer is spawned, compare each item with the task file's decisions. A decision covers an item when it names the test file, the return to Test, or the pull. Covered → run `node "{{LW_HOME}}/hooks/lw.mjs" accept-locks --reason "<that decision in words>" [--restart] [<path>…]` without asking the user (paths for `lockedAfterBuild`, `--restart` for `forcedRestartAfterBuild`). No decision covers an item → leave it to the reviewer, unchanged.

## Simplify

A read-only reviewer proposes cuts to the diff, you ask the user which to apply, and the existing roles apply only the approved ones. It never blocks Review.

Skip this section, silently and with no log line, when any of these holds: `simplify` is `false` in `brief`'s `config`; the task is a small-tier feature; this is not round 1 of the final review scope (the task for standard, `whole` for large); a `- Simplify:` line follows the last `- Scope change:` line in `## Review log` (so it runs again after `- Scope change: siblings included`). A small-tier fix runs it.

A `- Simplify:` line ending in `— apply pending` is not a skip: an earlier run was interrupted after the user approved cuts, so skip the question, resuming at the Apply (step 5), taking the approved cuts only from this run's `Simplify:` decisions in `## Decisions` (the last ones written, above the pending `- Simplify:` line), never from a `kept as written` line or an earlier run's decisions.

1. **Propose.** Now spawn the `loopwright-reviewer` subagent and wait for its result. Give it only: the absolute task file path, the base commit, and "Follow `{{LW_HOME}}/prompts/simplifier.md`." Large tier: add "Scope: whole-branch review of all slices". On Claude Code pass `effort` = the `effort` from `brief`, as in Passes step 2. The result is one JSON object with `obvious` and `tradeoffs` lists. Invalid JSON → dispatch it once more asking for only the JSON; still invalid → append `- Simplify: skipped — invalid output` to `## Review log` and go to Passes.
2. Both lists empty → append `- Simplify: nothing to cut` and go to Passes with no question.
3. **Ask.** Run `node "{{LW_HOME}}/hooks/lw.mjs" await-user "simplify"`, then ask everything in one prompt (Claude: `AskUserQuestion`, `multiSelect` for trade-offs; Codex and Junie: numbered text, the user replies with numbers):
   - `obvious` non-empty → one question listing each cut with its `lines`: apply all or skip all.
   - one trade-off cut → one question with its `change`, `lines` and `loses`: apply or skip.
   - 2–8 trade-off cuts → multi-select questions of up to 4 options each, split evenly into groups of 2 to 4 (an option is a cut: `change`, `lines`, `loses`); a selected option is approved.
   After the answer run `node "{{LW_HOME}}/hooks/lw.mjs" resume`.
4. **Record**, before applying anything. Each approved trade-off cut becomes a decision `D<n> [asked] Simplify: <location> — <change>; <lines> lines; gives up: <loses>`, approved obvious cuts (an apply-all answer) one decision line `D<n> [asked] Simplify: apply obvious: <location> — <change>; …`, and all declined cuts, trade-off cuts and the obvious cuts of a skip-all answer, one decision line `D<n> [asked] Simplify: kept as written: <location> — <change>; …` (each cut with its `change`, so it stays identifiable after applying other cuts moves line numbers), so Review does not report them. Then append `- Simplify: <o> obvious applied|skipped, <t> trade-off applied, <d> declined` to `## Review log`, ending it with ` — apply pending` when any cut is approved; write this line before applying, so a resume mid-apply does not ask again.
5. **Apply** each branch that has approved cuts; nothing approved → go to the Passes.
   - Approved cuts in locked test files first: `node "{{LW_HOME}}/hooks/lw.mjs" stage test`, then spawn the `loopwright-tester` subagent and wait for its result (on Claude Code pass `effort` = the output of `node "{{LW_HOME}}/hooks/lw.mjs" effort tester`; if the spawn rejects `effort`, spawn without it), with the task file path and the approved cuts verbatim for those files only. It applies them, reruns the tests and re-locks only those files. Then run `node "{{LW_HOME}}/hooks/lw.mjs" accept-locks --reason "<the decision in words>" <path>…` with those paths, so Review does not flag the re-lock.
   - Approved cuts in other files (the approved obvious cuts and the rest): `node "{{LW_HOME}}/hooks/lw.mjs" stage build`, then spawn the `loopwright-implementer` subagent and wait for its result, as in Build step 2 but with `effort` = the output of `node "{{LW_HOME}}/hooks/lw.mjs" effort implementer`, not the reviewer's. Its prompt contains the task file path and "Approved simplifications:" with the approved cuts verbatim (`location`, `change`); never your own summary. Keep its report verbatim. `Deviations` not "none" → handle them as in Build step 4; if that sends the task back to Plan or Test, remove the ` — apply pending` ending from the `- Simplify:` line before running `reopen`, so Test does not skip the tester.
   - `two-pass: on` → the second pass gets both implementer reports, Build's and this one.
   - After the last branch, remove the ` — apply pending` ending from the `- Simplify:` line. On a resume, skip an approved cut that is already applied.
6. Go on with the Passes.

## Passes

1. `node "{{LW_HOME}}/hooks/lw.mjs" stage review` (it updates the task file header `stage:` line; if it prints `"header": false`, set that line by hand).
2. **Blind pass.** Now spawn the `loopwright-reviewer` subagent and wait for its result. Give it only: the absolute task file path, the base commit, and "Follow `{{LW_HOME}}/prompts/reviewer.md`. Blind pass." Large tier: add "Scope: slice S<n> (its ACs; earlier slices passed)" or "Scope: whole-branch review of all slices". Never include the implementer report, chat history or your opinion. On Claude Code pass `effort` = the `effort` from `brief` on the spawn; if `brief` has no `effort` (it warns on stderr) or the spawn rejects `effort`, spawn without it (the agent file's effort applies). Use the same effort for the second pass.
3. **Second pass** (only if `two-pass: on`). Now spawn the `loopwright-reviewer` subagent and wait for its result, with the task file path, the base commit, "Follow `{{LW_HOME}}/prompts/reviewer.md`. Second pass.", and then "Verify the claims in this implementer report:" with the report verbatim (Simplify's apply report too, if it ran). Report no longer available → skip and note it in the log line.
4. **Cross-agent pass** (only if `crossAgentReview` is not `off`). `command -v <claude|codex>` fails → skip, note it. Otherwise, from the worktree root, set `PROMPT="Follow {{LW_HOME}}/prompts/reviewer.md. Task file: <abs path>. Base commit: <sha>. Blind pass."` and run (`LOOPWRIGHT_HOOKS=off` keeps loopwright's own hooks, such as the stop gate, out of the headless reviewer session):
   - claude (omit `--model` when the model is `inherit`; add one `"Bash(<cmd>:*)"` per check command in the task header; the `lw.mjs` entries allow only the read-only `status`, `check-locks` and `fingerprint`, in the quoted form the reviewer prompt uses and unquoted; the prompt must come after `--` because the tool flags take several values; `<effort>` is the `effort` from `brief`; omit `--effort` if it is missing):
     `LOOPWRIGHT_HOOKS=off claude -p --model <crossAgentReviewer.claude> --effort <effort> --output-format json --json-schema "$(cat "{{LW_HOME}}/schemas/verdict.json")" --allowedTools "Read" "Grep" "Glob" "Bash(git diff:*)" "Bash(git status:*)" "Bash(git log:*)" 'Bash(node "{{LW_HOME}}/hooks/lw.mjs" status)' 'Bash(node "{{LW_HOME}}/hooks/lw.mjs" check-locks)' 'Bash(node "{{LW_HOME}}/hooks/lw.mjs" fingerprint)' "Bash(node {{LW_HOME}}/hooks/lw.mjs status)" "Bash(node {{LW_HOME}}/hooks/lw.mjs check-locks)" "Bash(node {{LW_HOME}}/hooks/lw.mjs fingerprint)" "Bash(<check command>:*)" --disallowedTools "Edit" "Write" "MultiEdit" "NotebookEdit" -- "$PROMPT"`
     The verdict is the top-level `structured_output` field.
   - codex (best effort, untested; omit `-m` when the model is `inherit`): `OUT="$(mktemp)"; LOOPWRIGHT_HOOKS=off codex exec --sandbox read-only --output-schema "{{LW_HOME}}/schemas/verdict.json" -o "$OUT" -m <crossAgentReviewer.codex> "$PROMPT"`, then read the verdict from `$OUT`.
   Any error, timeout or unparseable output → skip and note it. This pass never blocks on its own failure. A check-command failure reported only by this pass that looks sandbox-caused (permission denied, read-only filesystem) is noted in the log, not counted as blocking.
5. A subagent reply that is not one JSON verdict → dispatch it once more asking for only the JSON; still invalid → stop and show the user.

## Outcome

Human gates: before you ask the user anything in this stage (an undecided finding, the fix-round cap, an invalid verdict; `AskUserQuestion` or a turn-ending question), run `node "{{LW_HOME}}/hooks/lw.mjs" await-user "<what you are waiting for>"`, so the stop gate lets you end the turn. After the user answers, run `node "{{LW_HOME}}/hooks/lw.mjs" resume`. (`stage` and `verdict` also clear it.)

Merge all passes: union of `blocking`, union of `undecided` (drop exact duplicates by location and expectation), sum of `droppedCount`. Decide from the arrays, not from the `pass` fields.

- **Blocking** present → `node "{{LW_HOME}}/hooks/lw.mjs" verdict fail --round <n>`. Fix rounds used = n − 1. If that reaches or exceeds the `fix-round cap`, stop: show every open finding and let the user decide (raise the cap, fix by hand, or accept). Otherwise show the findings briefly and run `/loopwright-build` with the Blocking findings verbatim; then review again (round n + 1). Undecided findings of this round are only counted; the next round re-checks them.
- Only **Undecided** → present each to the user, one at a time (Claude: `AskUserQuestion`; Codex: numbered text), with its location, expectation and proof; options: fix or dismiss. Record each answer under the round's log line: `  - U<k> <location>: fix|dismissed — <user's reason>`. Any "fix" → `verdict fail --round <n>` and Build with those findings, same cap rule. A dismissed re-lock or restart finding also runs `node "{{LW_HOME}}/hooks/lw.mjs" accept-locks --reason "<user's reason>" [--restart] [<path>…]`, so it is not asked again for that re-lock or restart. Every other Undecided finding is asked as above, each round. All dismissed → pass.
- An undecided finding the user wants resolved by changing the plan or a locked test (not just the code) → offer to go back: after `verdict fail --round <n>`, `await-user` and the answer's `resume`, run `node "{{LW_HOME}}/hooks/lw.mjs" reopen <plan|test> "<reason>"` with the user's reason (it sets the header `stage:` line, and `plan: draft` for plan; if it prints `"header": false`, set those lines by hand), then continue with `/loopwright-plan` or `/loopwright-test`. Run it only after the user chooses it.
- Nothing open → `node "{{LW_HOME}}/hooks/lw.mjs" verdict pass --round <n>`.
- Fix tasks, sibling gate: asked once, at the final pass (the task review for small/standard, the whole-branch review for large), never after a slice review. A passing slice review only records its merged `siblings` (union from all passes, dropping exact duplicates by `path` and `line`) as `  - Sibling <path>:<line> — <why>` lines under its log line, then the slice loop goes on.
  - At the final pass, take the merged `siblings` of this verdict plus every `Sibling` line after the last `- Scope change:` line, dropping duplicates by `path` and `line`. Non-empty → run `node "{{LW_HOME}}/hooks/lw.mjs" verdict pass --round <n> && node "{{LW_HOME}}/hooks/lw.mjs" await-user "siblings of the fixed bug"` as one call, in this order because the verdict clears the wait; list each sibling (`path:line`, why), then ask one question for the batch, recommendation first: include the siblings (also fix them), or list them as follow-ups. After the answer run `node "{{LW_HOME}}/hooks/lw.mjs" resume`.
  - Include → append `- Scope change: siblings included` to the review log, run `node "{{LW_HOME}}/hooks/lw.mjs" reopen plan "include siblings in the fix"` (it sets the header `stage:` and `plan: draft` lines; if it prints `"header": false`, set them by hand), then continue with `/loopwright-plan` (one `[repro]` criterion per sibling; Test locks the new repro tests and existing locks stay; Build and Review run again with a fresh fix-round budget, because rounds are counted after the scope change).
  - No (follow-ups only) → write the siblings under `## Follow-ups` in the task file (`path:line — why`) and go to `/loopwright-done`.

Once the outcome is known (after the user's undecided answers) and before the verdict command, append one line to `## Review log`, followed by its `U<k>` lines if any:
`- R<n>: <pass|fail> — <k> blocking, <m> undecided, <d> dropped — <key finding one-liners>; <skipped-pass notes>`
Large tier: `- R<n> S<k>: …` for a slice, `- R<n> whole: …` for the whole-branch review.

## After a pass

- small/standard → `/loopwright-done`.
- large → mark the slice `S<n> [passed]`; a `[todo]` slice remains → ask the question below, then `/loopwright-test` (or the fresh-context steps). When the last slice passes, run this skill again with scope `whole` (the diff against the base commit, all ACs); its fixes go through Build without new tests. Whole-branch pass → `/loopwright-done`.
- Large, after marking the slice `[passed]`, and a [todo] slice remains: ask one question, continue here or continue in a fresh context, with the reason in one sentence, stated as a tradeoff: later turns re-read the whole conversation, so a fresh context saves tokens when much of the task remains (several slices left), but the new session rewrites the cache, which can cost more than it saves when little remains; nothing is lost either way because the task file holds the plan. Not asked after the last slice, after a whole-branch review, or on a small or standard task. Run `node "{{LW_HOME}}/hooks/lw.mjs" await-user "<reason>"` before asking and `resume` after the answer. On "continue in a fresh context", in this order:
  1. Append `## Notes for Done` to the task file (add to it if it exists): up to five lines of things learned so far that Done may propose for `AGENTS.md`.
  2. Re-read the task file and write any decision made in this conversation that it is missing.
  3. Run `node "{{LW_HOME}}/hooks/lw.mjs" stage test` (it updates the header; if it prints `"header": false`, set the `stage:` line by hand), so the next session resumes at the next slice's Test and not in Review with no slice in scope.
  4. Tell the user what to type, by tool: Claude Code "`/clear`, then `/loopwright-flow`" (`/compact` also works and keeps a summary); Codex and Junie: start a new session and run the flow. End the turn. If the user's next message arrives in the same session, continue with `/loopwright-test` as usual.
- Any code edit after a pass makes the verdict stale; review again.
